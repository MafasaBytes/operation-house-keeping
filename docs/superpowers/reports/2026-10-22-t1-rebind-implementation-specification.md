## 1. Objective and boundaries

**What the tool is:** a small, stdlib-only utility, `tools/fixtures/t1_rebind.py`. It renders candidate
synthetic input records bound to one new `ct.build.v1` digest, so that a future installed synthetic workflow
can run. It is not an authoring product. It never:
- invokes or imports the application or backend;
- approves anything, or issues runtime authority;
- fabricates or inherits attestation text;
- edits simulator output;
- overwrites an earlier stage.

**Where it sits, and why:**
- **Source manifests stay unchanged.** It sits outside `applications/` and `backend/`, so it adds nothing to
  the source manifest that `measurement_build.identity()` hashes.
- **Build identity can still change.** `nm.build` also records the checkpoint (commit). A commit that adds
  the tool therefore changes the build digest even though the source manifest is unchanged. Under L1's
  installed mode the checkpoint comes from the release record.
- **Consequence:** commit the tool together with, or before, release commit `C`, and render inputs only
  after the release build digest of `C` exists (§10).

**Identity findings carried forward:**
- The reconciliation's identity findings (§3 there) stand: all five workflow commands use
  `ExecutableBuild → measurement_build.identity()`, and no identity-provider change is proposed.
- **One correction to the reconciliation's §4.2 text.** That file says the evidence `id` embeds "the first
  60 hex characters" of J. The producer rule is **59** characters:
  - `'E-t1-' + target_digest[:59]` (`t1_acquisition.py:99`; checked again at `t1_oracle.py:120`);
  - the retained identifier `E-t1-11669422…a922c30` has 59 hexadecimal characters [OBJ].
  The reconciliation file stays unchanged; this specification governs that detail.

## 4. Field-level correctness rules (no blind rewriting)

1. **Rule table, not text replacement.** Every change is one entry: (record role, JSON pointer, dependency
   role). The tool reads the value at that pointer, and for a typed reference requires all of:
   - an object with exactly the keys `kind` and `sha256`;
   - `kind` equal to the dependency's schema kind;
   - `sha256` equal to the dependency's *historical* digest.

   Only then does it set `sha256` to the dependency's new digest. A list rule (`permitted_*builds`) requires
   the source list to be exactly `[historical_build]`. No other bytes change.

2. **Source completeness check (refuses; never rewrites).** Before rendering, the tool walks every value of
   all 69 source objects (the opaque ones are only hashed). It refuses `REBIND_UNMODELLED_DEPENDENCY` if:
   - a to-be-replaced historical digest (the 10 role digests, the 9 pinned `prior_bundle` digests or the
     historical build)
     appears **anywhere other than a rule pointer**; or
   - a prefix of 12 or more hexadecimal characters of one appears, other than the modelled evidence `id`
     (rule EV-ID, which is generated, not rendered).

   This turns an unknown dependency into a stop-and-amend-the-specification event.

   **The opaque objects are only hashed.** For the pilot, the ten opaque `ct.evidence-content` objects were
   checked during review and contain no historical digest or prefix.

3. **Output diagnostic scan (disclosure, not repair).** After rendering, the tool scans its outputs for those
   historical digests and prefixes. Each hit is classified:
   - `in_attestation_text` (inside `/provenance/label` or `/provenance/basis`): reported in the packet, never
     changed;
   - `in_lineage` (the review and packet files): expected;
   - **any other location in a rendered or copied object: an internal error.** The tool refuses
     `REBIND_INTERNAL` and leaves `PARTIAL` (§5.4). This means the rule table or the completeness check has a
     bug.

   The scan never edits identifiers, prose or attestation text.

4. **Canonical round trip.** Each source record must satisfy `canon(parse(bytes)) == bytes`, and parsing
   refuses:
   - duplicate keys;
   - `NaN` or `Infinity`;
   - depth over 24, more than 65,536 nodes, or a string over 4,096 UTF-8 bytes.

   These are the limits of `t1_records.parse` (`t1_records.py:23–55`).

   **Floats are accepted, as the application accepts them.** Legitimate retained records contain float
   literals: baseline evidence `b49f67d4…` (`1794.0`), preset `c6f0cafa…` (`3721.845`, `45.2`) and evidence
   `686ecc43…` (`112.0`). All of them pass the canonical round trip, which preserves them. Refusing floats
   would refuse the pilot itself (review finding B1).

   The 9 rendered kinds hold no floats. A float inside any of them would be outside the rule table, so it is
   refused as `REBIND_INPUT_INVALID`.

   Each rendered record is serialized only with `canon`.

5. **Schema preservation by construction.** The tool changes only:
   - SHA-256 strings inside typed references whose `kind` stays the same;
   - `permitted_*builds` lists, set to one non-zero 64-hex digest (schema: 1–8 unique sha256 items);
   - two attestation strings, checked to the schema limits: label 1–128 characters, basis at most 1,024
     characters, no C0 control characters.

   Full schema validation of rendered output uses the application's own validators **in tests only** (§9);
   the tool itself imports no repository module.

6. **What makes rule EV-ID safe.** The tool never computes or writes an evidence `id`. In stage 3 it only
   *checks* that M′'s evidence `id` equals `'E-t1-' + J′[:59]`, matching the producer's construction rule.

### 5.4 Exclusive output, path rules and partial writes

**Checks on `--out`; any failure refuses `REBIND_OUTPUT_UNSAFE`:**
- It must not exist.
- Its parent must exist, be a real directory, and contain no symlink component (checked with `lstat` on
  every component).
- It must not resolve inside any input directory.
- It must not resolve inside the repository containing the tool (the parent of `tools/`). This keeps the Git
  tree clean, which matters because Git mode refuses a dirty tree, and keeps `applications/` and `backend/`
  untouched.

**Write sequence:**
1. `os.mkdir(out, 0o700)`.
2. Create `PARTIAL` with `O_CREAT|O_EXCL|O_NOFOLLOW|O_WRONLY` (mode 0o600) and fsync it.
3. Create subdirectories with `mkdir`, and each file with `O_EXCL|O_NOFOLLOW`, fsyncing each file.
4. Write `packet/APPROVAL-PACKET.json`, then `REBIND-REVIEW.json`, last.
5. Fsync the directories, unlink `PARTIAL`, and fsync `out`.

**If anything fails after `mkdir`:** stop, leave `PARTIAL` in place, refuse with exit 5, and delete nothing.
A later stage refuses an input stage directory that:
- contains `PARTIAL`;
- lacks its review; or
- has a review digest different from the `--expected-stageN-review-sha256` argument.

It also refuses if any file disagrees with the review inventory (extra, missing, size or hash). Re-running
into an existing `--out` is always refused; a corrected run uses a new path.

**Output caps:** stage 1 at most 40 files and 2 MiB; stage 2 at most 16 files and 1 MiB; stage 3 at most 32
files and 1.5 MiB.

### 5.5 Deterministic review record (`REBIND-REVIEW.json`)

**Format:** pretty JSON (`indent=1, sort_keys=True, ensure_ascii=False`) with a final newline. It contains
no timestamps, hostnames, user names or absolute paths, so identical inputs give identical bytes.

**Fields:**
- `schema: "t1-rebind-review.v1"`, `stage`, `tool_edition: "t1-rebind.v1"`;
- `tool_sha256`: the tool's own file bytes, read through the same bounded reader;
- `source_pins_sha256`, `attestations_sha256`, `build: B`;
- `inputs`: by role, `{sha256, bytes}`, including earlier review digests, B0′ file digests and the M′ manifest
  pin;
- `outputs`: sorted by relative path; each `{path, sha256, bytes, kind, disposition}`, where disposition is
  `rendered`, `copied_unchanged` or `copied_generated`;
- `changes`: for each rendered record, a list of `{pointer, old, new, rule}`. Provenance text changes show the
  full old and new strings;
- `edges`: `{from_role, pointer, to_role, to_sha256}` for every re-pointed reference;

## 8. Owner approval and execution boundaries

### 8.1 States

| State | Created by | Means | Does **not** mean |
|---|---|---|---|
| Candidate rendered | A tool run (itself a separately authorized execution) | Bytes and digests exist; review and packet written | Approval, or any authorization to run the application |
| Owner approved | The owner writes a separate approval record (§8.4) binding the candidate digests | The owner accepts these exact bytes for the stated role and scope | Execution authorization |
| Execution authorized | An explicit owner execution grant naming the command, arguments, pins and the approval record digest | One bounded run of one maintained command | Approval of any other bytes, or a later run |

A digest, a review file, a schema check or a successful tool exit is **never** approval.

### 8.2 Approval points

| Point | Records and role | What approval authorizes | What it excludes | Blocks until approved |
|---|---|---|---|---|
| **AP-S1** | policy′ (policy owner: B as the sole permitted build, and the policy text); P′ (proposer); A0′ (evaluation issuer: selection evaluation of P′ in declared window 2026-10-01 to 10-31) | Use of these bytes as inputs to EX-1 | Any other build; any wall-clock authority; adoption; physical acquisition | EX-1 `checked-selection-evaluate` |
| **AP-S2** | S′ (policy owner: B as producer and checker build); X′ (proposer: inheriting B0′'s selection); J′ (proposer: the synthetic target and window); E′ (execution issuer: T1 execution of X′, declared 2026-10-05 08:00–18:00Z); G′ (execution issuer: simulation only, all other grants false) | Use as inputs to EX-2 | Physical acquisition, evaluation, adoption | EX-2 `t1-simulation-run` |
| **AP-S3** | R′ (proposer: the reassessment request citing M′'s actual evidence′ and scalar) | Use as input to EX-3 | Evaluation; any claim beyond the synthetic result | EX-3 `t1-reassessment-prepare` |
| **AP-S4** | A′ (evaluation issuer), prepared outside the tool after H′ | Use in EX-4 | Adoption | EX-4 `t1-reassessment-evaluate` |

**Roles:**
- The role string inside each record is fixed by schema. It is an unauthenticated label
  (`authenticated: false`), not an identity.
- In this synthetic development profile, the project owner decides every role. A future multi-party profile
  could assign them to different people; that is out of scope.
- Supplying the attestation JSON does not make anyone an issuer.

| Grant | Command |
|---|---|
| EX-0 | Running the tool, for each stage. EX-0 for stage 2 and stage 3 must cite the approval-record digest of every earlier stage (AP-S1, and AP-S2 for stage 3), and the operator checks that its candidate digests equal the review pins supplied |
| EX-1 | `checked-selection-evaluate` |
| EX-2 | `t1-simulation-run` |
| EX-3 | `t1-reassessment-prepare` |
| EX-4 | `t1-reassessment-evaluate` |
| EX-5 | `t1-workflow-verify` |
| EX-6 | `checked-reassessment-replay` |

### 8.4 Review packet (tool output) and approval record (owner output)

**`packet/APPROVAL-PACKET.json`** (deterministic, pretty JSON). For each record of its stage it gives:
- role, kind, new SHA-256 and byte count;
- **the complete candidate bytes**, as the exact canonical UTF-8 text;
- every changed pointer, old → new;
- dependencies (role → digest);
- the attestation text exactly as supplied, with `matches_historical_text`;
- the record's own declared `valid` window or times, with the fixed interpretation: *declared synthetic
  instants checked against declared request and acquisition times, not the wall clock and not the approval
  date*;
- the synthetic-scope statement: *unauthenticated synthetic development premise; no physical, operational or
  adoption authority*;
- what approval authorizes and what it excludes (§8.2);
- `blocked_next_operation`: the exact command template with its pins, labelled `NOT AUTHORIZED BY THIS
  PACKET`.

**Approval record** (`t1-rebind-owner-approval.v1`):
- **Who writes it:** the owner, or their delegate on explicit instruction, as a separate file. Its natural
  home is the runtime evidence directory or an owner decision report.
- **Where it never goes:** into any objects directory or any application schema record. No application
  schema gains an approval field.
- **Fields:**
  - `approval_point`;
  - `stage_review_sha256` and `packet_sha256`;
  - `candidates`: a list of `{role, kind, sha256, bytes}` that must cover every record of the point;
  - `attestations_sha256`;
  - `decision`: `approved` or `rejected`;
  - `authorizes`, `excludes` and `next_operation_requires_separate_grant: true`;
  - `recorded_on` (a date).
- **Who reads it:** neither the tool nor the application. The operator of a later execution grant verifies
  that the grant's pins equal the record's candidate digests before launching.
- **Partial approval is not supported.** A rejection of any record in a stage means re-rendering that stage,
  and every later stage, into new directories.

**Not done in this preparation:** no approval is populated, no attestation text is chosen, and no runtime
authority object is issued.

## 10. Fit into L2

**The handoff from release construction to input preparation**, superseding step 5 of the reconciliation's
§5.3 in detail only:
1. **Release build:** commit `C` contains the L2 files and this tool. Build the staging release and run
   `release_check`, which yields the actual release `ct.build.v1` digest **B** through the channel chosen in
   OD-L2-B.
2. **EX-0 stage 1** with B → AP-S1 → **EX-1** `checked-selection-evaluate` on the staging install produces
   B0′. Stage 2 then confirms `B0′/build.json` hashes to B.
3. **EX-0 stage 2** → AP-S2 → **EX-2** `t1-simulation-run` produces M′.
4. **EX-0 stage 3** → AP-S3 → **EX-3** prepare produces H′. A′ is prepared, then AP-S4.
5. **EX-4 to EX-6:** evaluate, verify and replay, completing the installed workflow.

**Staging versus VM:**
- **Equality check required.** Before any build-bound input is used on the VM, compare the VM's actual
  `ct.build.v1` digest from its own `release_check` with B, byte for byte. Matching version labels, paths or
  package names prove nothing. Equality also needs identical release bytes, the same prefix and the same
  glibc `libc_ver`.
- **If they differ:** stop. Propose a new input set bound to the VM digest, with new approvals. **Never**
  widen `permitted_builds` automatically. This tool deliberately takes a single B.
- **B0′ is run-specific** (`created_at_utc`), so the VM cannot regenerate an identical B0′. With equal digests,
  carry B0′, the rendered inputs and their approval records to the VM by hash.
- **If acquisition is repeated on the VM,** compare its evidence′ digest with staging's. If they are equal,
  R′ (and A′) remain valid. If not, re-render stage 3 and re-approve R′ and A′. The M′ manifest may differ
  through platform-dependent diagnostic database bytes without affecting R′.
